[← Back to master tracker](./README.md) · [← Back to EYE category](./EYE.md) · [← Build plan](./EYE-PLAN.md)

_Tracking model: face landmarks (eye-ring region - lower lash-line/waterline arc, nose tip). Depends on the shared face-landmark engine — see [README.md](./README.md#shared-prerequisites-ye-pehle-banao--sabko-block-karte-hain)._

> **Per-subcategory tracker** — same convention [EYELINER.md](./EYELINER.md) established: as a subcategory gets built, it gets its own dedicated tracker file and [EYE.md](./EYE.md)'s own inline checklist for it gets replaced with a summary-row + link.

> Built directly on top of EYELINER's own machinery, exactly per [EYE-PLAN.md](./EYE-PLAN.md)'s build order ("EYELINER + KAJAL together - same underlying primitive, two subcategories for the price of one build") — no new engine class, no new UI component, no new landmark set. The only real code addition was extracting EYELINER's own per-eye orchestration (`renderEyelinerForEye`) into a finish-agnostic `renderTaperedStrokeForEye` (takes an already-resolved tuning object instead of an EYELINER-specific pattern id), so `applyKajalEye` ([`utils/tryon-utils/eye.ts`](../../src/utils/tryon-utils/eye.ts)) is a thin wrapper around the exact same primitive, just tracing the lower lash-line arc instead of the upper one. `EyeEngineBase` gained one switch case (`'KAJAL'`) and lost its old `UNSUPPORTED_EYE_FINISHES` entry for it.

## Design notes

- **Exactly EYELINER's own primitive, a different arc**: `renderTaperedStrokeForEye` (renamed from `renderEyelinerForEye` when this finish was added) has no idea which finish is calling it - it just traces whichever arc it's handed (`primaryArc`), tapering width per `t` and optionally blurring, exactly as EYELINER's own patterns do. `applyKajalEye` passes `LEFT/RIGHT_EYE_LOWER_INDICES` as `primaryArc` (EYELINER passes the upper arc); the upper arc is passed as `secondaryArc` purely for interface-shape consistency, since `KAJAL_PATTERN_TUNING` never sets `underlinerWidthRatio` and that parameter is simply never read for KAJAL. This is the entire structural difference between the two finishes, matching [EYE-PLAN.md](./EYE-PLAN.md)'s own build note ("no new code beyond parameter tuning once the shared primitive exists").
- **4 patterns, no wing math needed**: Thin Waterline and Tightline Lower Lash are the same uniform-taper shape EYELINER's Classic Thin/Tightline use, just on the lower arc and at KAJAL-appropriate widths. Smudged/Smokey reuses the same `blurRatio` + `ctx.filter` blur pass SMOKEY_SMUDGED (EYELINER) established. Full Bold Kohl's "extending slightly past the outer corner" (per [EYE-PLAN.md](./EYE-PLAN.md)'s own pattern description) is handled by a wider `tipWidthRatio` alone rather than `buildWingPoints` - kajal's own outer-corner extension is a much shorter, subtler flick than EYELINER's Winged/Double Wing, close enough to "the line just stays thick to the very end" that a real wing would be over-engineering for it. None of `KAJAL_PATTERN_TUNING`'s 4 entries set `wing`/`secondWing`.
- **Inherits EYELINER's own hard-won fixes for free**: because this is the _same_ `fillTaperedPath`/`outwardNormalsAlongPath` code EYELINER's own gap/fragmentation bug was fixed in (see [EYELINER.md](./EYELINER.md)'s own Design notes on the quad-decomposition fix), KAJAL never had that bug to begin with - re-verified via the same flood-fill connected-component technique on the real photo used for EYELINER's own verification (see below), rather than assuming it "should" be fine by inheritance alone.
- **Pattern-preview icons, matching EYELINER's visual language on purpose**: the 4 icons (`public/images/tryon/eye/kajal/*.webp`) reuse the exact same base template EYELINER's 7 icons use (light-gray lid-crease arc, gray iris + white highlight, thin black "unlined" reference line) - generated with a one-off `canvas`-package Node script (not checked in - same "temporary tooling, not shipped code" treatment as this session's other diagnostic scripts), converted PNG→WebP via `cwebp` (`node-canvas`'s own `toBuffer('image/webp')` isn't supported by the installed build). The one deliberate difference from EYELINER's icons: the bold product stroke sits on the _lower_ margin instead of the upper one, so the two pattern pickers are visually distinguishable at a glance before ever reading a label. Two much older, differently-styled placeholder images (`Bold.webp`/`Classic.webp`) were already sitting in that folder from an earlier scaffolding pass, unrelated to and not reused by these 4 - left in place since nothing currently references them and deleting other pre-existing assets wasn't this task's call to make.
- **A real, pre-existing default-pattern gap fixed while adding this finish**: `EyeEngineBase.applyEffect`'s pattern fallback used to be a flat `state.pattern ?? EYELINER_DEFAULT_PATTERN` - harmless while EYELINER was the only pattern-bearing finish, but wrong the moment a second one with its own separate id namespace existed (a KAJAL selection with no pattern picked yet would've silently tried to render with an EYELINER id, matching nothing in `KAJAL_PATTERN_TUNING`, rendering blank). Fixed with a finish-keyed `EYE_DEFAULT_PATTERNS` map. A second, related gap: `TryOnModal`'s own `initialState.pattern` was `flow.engineState?.pattern ?? undefined` - the comment there claimed this fell back to `EyeEngineBase.getInitialState()`'s own default, but object-spread semantics don't work that way (`{...base, pattern: undefined}` really does end up `undefined`, it doesn't fall through to `base.pattern`), so on a fresh session the pattern picker showed _no_ swatch as selected even though something was still rendering underneath via the engine's own fallback. Fixed by having `TryOnModal` fall back to `EYE_DEFAULT_PATTERNS[tryOn.subCategory]` directly, so the picker's "currently applied" swatch matches what's actually rendered from the very first frame - verified live (Thin Waterline shows its check-circle/active border immediately on opening KAJAL, without touching the picker).
- **Verification done so far**: `tsc -b --force`, `eslint`, and the full `vitest` suite (80/80, including 6 new `applyKajalEye` smoke tests - all 4 patterns, one unrecognized-pattern-id case, and one EYELINER-id-cross-contamination case) all pass. Real-photo browser verification (North Indian model, Ruby Red, all 4 patterns): the lower-lash stroke renders symmetrically on both eyes for every pattern, visibly thickens Thin Waterline → Full Bold Kohl, and visibly softens for Smudged/Smokey; a flood-fill connected-component scan (same technique EYELINER's own wing-gap bug was diagnosed and fixed with) found exactly one connected blob per eye for both Thin Waterline (898px-scale default) and Full Bold Kohl (1066px/1035px, left/right) - no fragmentation on either eye.
