# EYEBROW Try-On Tracker

[← Back to master tracker](./README.md) · [← Back to EYE category](./EYE.md) · [← Build plan](./EYE-PLAN.md)

_Tracking model: face landmarks (eyebrow ring, nose tip). Depends on the shared face-landmark engine — see [README.md](./README.md#shared-prerequisites-ye-pehle-banao--sabko-block-karte-hain)._

> **Per-subcategory tracker** — same convention [EYELINER.md](./EYELINER.md)/[KAJAL.md](./KAJAL.md)/[EYESHADOW.md](./EYESHADOW.md) established: as a subcategory gets built, it gets its own dedicated tracker file and [EYE.md](./EYE.md)'s own inline checklist for it gets replaced with a summary-row + link.

> **The first EYE finish built on a real, directly-tracked closed region**: EYELINER/KAJAL trace an open arc, EYESHADOW washes a _synthesized_ region (an offset of the lash line, since no crease landmark exists) - EYEBROW is the first one where MediaPipe already tracks the whole region directly as a closed ring (`LEFT/RIGHT_EYEBROW_INDICES`, the same points FACE's own full-face washes already use for their exclusion holes). 5 patterns: Bold/Defined Fill, Soft Powder Fill, and Ombre Brow are closed-region fills (flat, blurred, or gradient); Natural Hair-Stroke and Feathered/Fluffy draw many individual tapered strokes across the region instead, for a hair-like texture - procedural canvas math with deterministic per-stroke variation, not a texture image asset.

## Design notes

- **A real closed ring, not first/last-point ordering**: `LEFT/RIGHT_EYEBROW_INDICES` (10 points each) trace continuously around the brow's own physical loop - unlike the open eye arcs, where `orderInnerToOuter` decides which literal endpoint is inner vs outer, a ring's own first/last points are just wherever the index list happens to start/stop going around the loop, not necessarily either anatomical end. `findInnerOuterPoints` instead scans every point in the ring directly for whichever one sits closest to (inner) and farthest from (outer) the nose tip - correct regardless of how the ring's own indices happen to be ordered, needed for Ombre Brow's own gradient axis.
- **`traceEyebrowPath` - light rounded-corner trace, not fully curve-smoothed**: at each of the ring's own points (10, or 11 once the tail-landmark fix below landed), pulls back a small fraction along both adjoining edges and connects those two points with a `quadraticCurveTo` through the real vertex - see the fix bullets below for the full history of why this landed here (not full curve-smoothing, not pure straight lines either).
- **"Too curvy/rounded, doesn't cover the real brow" - fixed against commverse's own reference implementation**: reported directly against a real render - both eyebrows filled as a uniformly round arch that read as a generic idealized brow shape rather than tracking the model's own actual (more angular, less symmetric) eyebrow underneath. Checked `src/commverse`'s own eyebrow rendering (`utils/index.ts`'s `clipLipsOnFace`/`drawEyebrow`) directly: it traces the same kind of raw landmark ring with **plain straight lines** (`moveTo`/`lineTo` per point, `closePath()`) and no smoothing step anywhere. Our own `traceEyebrowPath` was instead running a quadratic-curve-through-midpoints pass (the same technique borrowed from FACE's closed regions) - fine for FACE's own much denser landmark rings, but at only 10 sparse eyebrow points that "cut every corner" technique measurably inflates the shape into a rounder arch than the real, more angular brow silhouette the sparse points actually describe. Fixed by switching `traceEyebrowPath` to the same plain straight-line trace commverse uses - no new landmark indices needed (`LEFT/RIGHT_EYEBROW_INDICES` unchanged), purely a tracing-technique change. `renderEyebrowHairStrokes` (Natural Hair-Stroke/Feathered-Fluffy) was untouched, since it already builds its own strokes directly from the ring's raw points rather than going through `traceEyebrowPath`. Verified against the North Indian/Ruby Red photo across all 5 patterns (plus BROWGEL, which shares `fillEyebrowRegion`) - the brow shape now reads as a faithful, angular trace of the real eyebrow instead of a rounded blob, on both eyes.
- **"Still not covering the full eyebrow, especially the ends" - a second, separate fix on top of the straight-line change**: reported again, directly against a real render, right after the straight-line fix above landed - the straight lines were now faithful to the _landmark ring's own_ shape, but the ring itself still sat visibly inside this model's real (fuller) brow, most noticeably at the tail, where real hair tapers off past the ring's last point. Checked commverse's own extra tail-side landmark (`156` left / `383` right, `data/index.ts`) as a possible fix, the same way the EYELINER corner-fade fix borrowed extra landmarks from commverse - but a debug overlay (drawing both the ring's own 10 points and 156/383 directly on a real render) showed 156/383 sit _down_ toward the eye's own outer corner, not further _out_ along the brow's own taper; splicing either straight into the ring would drag the tail down into bare skin, not extend it sideways - wrong fix for this specific symptom. Instead added `dilateAroundCentroid` (utils/tryon-utils/eye.ts): scales every ring point outward from the ring's own centroid by a fixed `EYEBROW_REGION_DILATION_RATIO` (originally `0.16`, later tuned down - see below) - a plain geometric margin, same "synthesize the extra coverage directly" philosophy as `renderCornerFadeTail`, just applied to a closed region instead of a stroke's own endpoint. Applied once, immediately after `toPoints`, in both `applyEyebrowEye` and `applyBrowgelEye` - so every downstream use of the ring (the fill boundary, `renderEyebrowHairStrokes`' own edge sampling, `findInnerOuterPoints`' inner/outer picks, Ombre Brow's gradient axis) sees the same enlarged region consistently, from one change per entry point. Verified against the North Indian/Ruby Red photo across all 5 EYEBROW patterns plus BROWGEL: the tail and top-arch both now read as fully covered, with no bare hair visible past the fill's own edge on either brow.
- **"Middle 3 patterns going way too far outside, first and last are correct" - a tail-taper follow-up was reverted**: after the dilation fix above, a hard "cut" was still visible at the fill patterns' own tail corner, so a follow-up change added `traceEyebrowPathTapered` - extending the fill boundary's two edges along their own local tangent at the tail, mirroring `renderCornerFadeTail`. That change only touched `fillEyebrowRegion`'s own trace call, never `renderEyebrowHairStrokes` - so Soft Powder Fill/Bold/Defined Fill/Ombre Brow (the 3 fill patterns, sitting in the middle of `TEyebrowPattern`'s own declaration order between Natural Hair-Stroke and Feathered/Fluffy) ended up reaching visibly further out than Natural Hair-Stroke and Feathered/Fluffy (the first and last patterns, unaffected since they never call `traceEyebrowPathTapered`) - reported directly as those 3 overshooting past the other 2's own correct position, with an explicit instruction to match all 5 to the hair-stroke patterns' own extent. Fixed by reverting `fillEyebrowRegion` to trace the plain dilated ring (no extra taper) - the same boundary `renderEyebrowHairStrokes` already samples its own edges from - and deleting the now-unused `traceEyebrowPathTapered`/`extendAlongTangent`/`EYEBROW_TAIL_TAPER_LENGTH_RATIO`. All 5 patterns now share exactly one region (the dilated ring), so there's no more per-pattern position drift to begin with. Verified against the North Indian/Ruby Red photo: all 5 patterns' own tail extent now lines up pixel-for-pixel with each other.
- **"The ends' length is too much, turn it down" - `EYEBROW_REGION_DILATION_RATIO` reduced from `0.16` to `0.08`**: with all 5 patterns sharing one region again (previous fix), the complaint shifted from _mismatch between patterns_ to the _shared_ length itself - `dilateAroundCentroid` scales every point's distance from the ring's own centroid, so points already farthest from center (the inner and outer corners - the brow's own "ends") move by a proportionally larger absolute amount than points near center (the top/bottom arc), reading as visibly elongated tips rather than a uniform margin. Confirmed directly: the approach itself (uniform dilation, all 5 patterns sharing it) was correct, just the ratio was too aggressive - simple to halve rather than redesign. Verified against the North Indian/Ruby Red photo across all 5 patterns: the ends now read as a natural, proportioned taper instead of visibly stretched-out points.
- **"Too curvy" again (this time meaning jagged, not rounded) + "make the ends a little sloppy" - light corner-rounding added on top of the straight-line trace**: with the dilation ratio tuned down, the complaint shifted a third time - the _pure_ straight-line trace (from the earlier commverse-matching fix) reads as visibly kinked at each of the 10 landmark points once you're not distracted by an over/under-sized region, and the two real tail/inner-corner joints specifically looked like an unnaturally precise geometric point rather than a real brow's own soft taper. `traceEyebrowPath` now rounds every vertex by a _small_ `EYEBROW_CORNER_ROUND_RATIO` (`0.18`) - pull back along both adjoining edges by that fraction and connect the two pulled-back points with a `quadraticCurveTo` through the real vertex, unlike the original (deleted) midpoint technique which always rounded a full 50% of every edge and inflated the whole shape. The ring's own two real corners (where the upper and lower edges actually meet - found the same way the tail-taper fix identified them, by comparing each corner's own distance to `findInnerOuterPoints`' `outer`) get a separate, larger `EYEBROW_END_ROUND_RATIO` (`0.45`) for a deliberately looser, softer taper there. `renderEyebrowHairStrokes` still doesn't call `traceEyebrowPath` at all, so this only affects the 3 fill patterns' own boundary, same scoping as every fix in this section. Verified against the North Indian/Ruby Red photo (Bold/Defined Fill): the edges between landmarks now read as smoothly rounded rather than kinked, and both tail ends taper to a soft, slightly loose point instead of a sharp geometric corner.
- **"Check commverse again, its position is proper" - adopted commverse's real tail landmark instead of continuing to synthesize a margin, then a follow-up request to loosen the ear-side top further**: two synthetic fixes (`dilateAroundCentroid`, then `traceEyebrowPathTapered`) had been standing in for landmark data we didn't have - re-checked commverse's own `left_eyebrow_indices`/`right_eyebrow_indices` (`data/index.ts`) directly this time (not just the earlier `clipLipsOnFace` tracing-technique check) and found they include one extra real tail-side point (`156` left / `383` right) neither synthetic fix had matched; commverse's own rendering gets the tail's correct extent purely from that one point, with zero extra margin on top. Added the same point to `LEFT/RIGHT_EYEBROW_INDICES` (constants/tryon-constants/eye.ts, appended at the end of each array) and removed both synthetic fixes entirely (`dilateAroundCentroid`/`EYEBROW_REGION_DILATION_RATIO`, `traceEyebrowPathTapered`/`extendAlongTangent`/`EYEBROW_TAIL_TAPER_LENGTH_RATIO`) - real landmark data beats a geometric approximation of it. Kept the new point **out of** `renderEyebrowHairStrokes`' own ring (`applyEyebrowForEye` now slices it off via `.slice(0, 10)` before passing to hair-strokes): that point sits down toward the eye's own outer corner rather than along the brow's own hair line (confirmed via an earlier debug overlay), so hair-stroke patterns keep sampling their own edges from the original 10-point ring, which was already independently confirmed correct and left unaffected throughout. `traceEyebrowPath` itself also needed a rework here: with an 11-point ring (10 + the one appended tail point) the old half-split corner detection (`half-1`/`half`, `n-1`/`0`) no longer lands on the ring's real two corners, so it now finds the actual inner/outer vertices by matching `points` against `findInnerOuterPoints`' own `inner`/`outer` (nearest-point search) instead of assuming array-position symmetry - works regardless of how many points the ring has. A follow-up request ("make the ear-side end a bit more sloppy, from the top") added one more tier: the outer point's own _upper_ neighbor (whichever of its two adjoining vertices has the smaller y) gets an even larger `EYEBROW_OUTER_TOP_ROUND_RATIO` (`0.7`) on top of the general `EYEBROW_END_ROUND_RATIO`. Verified against the North Indian/Ruby Red photo across all 5 patterns: the tail now tapers to a soft point with full hair coverage and no hard cut, matching commverse's own reference shape, while Natural Hair-Stroke/Feathered-Fluffy remained visually unchanged from their own already-correct look.
- **Hair-strokes are procedural, not a texture asset**: `renderEyebrowHairStrokes` splits the 10-point ring into its two edges (first half/second half, the second reversed so both run the same rotational direction), smooths each into a dense point sequence, then for each of `strokeCount` strokes draws a single tapered segment (`fillTaperedPath`, the exact same ribbon primitive every other stroke-based EYE finish already uses) from a point on the lower edge to a point on the upper edge - comparing the two edge points' own y at render time (not trusting which constant array is "upper") to find which one is actually the base a hair grows from. `strokeJitter` (a deterministic sine-based hash, not `Math.random()`) varies each stroke's angle/length/width reproducibly, so the same photo always renders identically and this file's own smoke tests stay deterministic. `strokeAngleBiasDeg` blends each stroke's direction toward straight-up - 0 for Natural Hair-Stroke's own "lying along the brow's natural line" look, a much larger value for Feathered/Fluffy's "brushed up" soap-brow look - the only tuning difference between the two patterns.
- **Ombre Brow's gradient axis is the ring's own inner→outer line, not the eye's**: `ctx.createLinearGradient(inner.x, inner.y, outer.x, outer.y)` using the eyebrow ring's own `findInnerOuterPoints` result, lighter (`mixTowardWhite`) at the front/inner end, bolder (`mixTowardBlack`) at the tail/outer end - same per-channel math EYESHADOW already ported from FACE's own HIGHLIGHTER/CONTOUR.
- **Pattern-preview icons**: the 5 icons (`public/images/tryon/eye/eyebrow/*.webp`) reuse the same base template (light-gray lid-crease arc, gray iris + white highlight, thin black lash-line boundary) every other EYE finish's own icon set uses, generated with a one-off `canvas`-package Node script (not checked in, same temporary-tooling treatment as every other EYE finish's own icon generation), converted PNG→WebP via `cwebp`. A proper brow-arch shape (its own pair of quadratic curves, independent of the template's own decorative crease line) sits above the eye, styled per pattern - a neutral brunette tone for the 3 fill patterns, individual procedural hair-strokes (the exact same jitter/taper technique the real renderer uses, reimplemented for the icon script) for the other 2, which read as genuinely convincing individual-hair textures even at icon scale.
- **Verification done so far**: `tsc -b --force`, `eslint`, and the full `vitest` suite (95/95, including 7 new `applyEyebrowEye` smoke tests - all 5 patterns, one unrecognized-pattern-id case, and one EYELINER-id-cross-contamination case) all pass. Real-photo browser verification (North Indian model, Berry Wine, all 5 patterns): every pattern renders on both eyebrows following the real brow shape closely, with a visibly distinct look per pattern (Soft Powder's blur, Bold/Defined's crisp edges, Ombre's light-to-dark gradient, Natural Hair-Stroke's fine strand texture blending convincingly with the model's own real brow hairs, Feathered/Fluffy's more upward-brushed strokes) - and a pixel-diff between Bold/Defined Fill and Natural Hair-Stroke confirmed 7,705 genuinely changed pixels in the brow region.
