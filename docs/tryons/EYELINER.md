## Design notes

- **Shared tapered-stroke primitive**: har pattern upper lash line ke saath (`LEFT_EYE_UPPER_INDICES`/`RIGHT_EYE_UPPER_INDICES`, `constants/tryon-constants/eye.ts`) ek continuous filled path hai, ek per-`t` width function (`lashToWidth`) ke saath - inner corner ke kareeb thin, outer ke kareeb thicker, optionally outer corner ke paar ek curved "wing" extension mein continue karta hua. Classic Thin/Bold Thick/Tightline is ek primitive pe bas alag base/peak width ratios hain; Winged/Double Wing wing add karte hain; Smokey/Smudged ek `ctx.filter` blur pass add karta hai (same technique jo LIP ka apna `LINER` finish already establish kar chuka tha); Underliner ek second pass add karta hai jo lower arc trace karta hai. Saare widths/lengths eye ke apne detected width (inner-to-outer corner distance) ke ratios hain, fixed pixels nahi - same "feature ke apne size se scale karo" convention jo is app ka har doosra placement constant follow karta hai.
- **Mirror-safe geometry - is finish ka sabse hard part**: MediaPipe ke apne eye-ring indices "inner"/"outer" ki tarah side-independent labeled nahi hain, aur left/right eye arcs genuinely mirrored directions mein chalte hain. Do cheezein direction-agnostic honi zaroori thi taaki dono eyes pe correctly kaam karein:
  1. `orderInnerToOuter` - decide karta hai ki arc ka kaunsa end inner (nasal) corner hai, har end ke x-distance ko nose tip se compare karke render time pe, ek fixed index ko hamesha "inner" maanne ki jagah.
  2. `outwardNormalsAlongPath` - har path point pe width offset direction, _local path tangent_ se derive hui (har jagah correctly perpendicular, ek curving wing pe bhi, ek pure "centroid se door" direction ke ulat jo eye ke apne center se door "outward" ka matlab rakhna band kar deti hai). Tangent-perpendicular apne aap 180° se ambiguous hai har point pe, isliye sign ek baar decide hota hai path ke pehle point pe (centroid ke through) aur phir point-to-point continuity se propagate hota hai (har normal jo closest rahe, dot product se, pichle point ke apne chosen normal ke) - ek discrete parallel-transport, har point ko independently centroid ke against re-test karne ki jagah (iska ek earlier version, jo wing pe door apne neighbors se disagree kar sakta tha). Wing ki apni launch direction bhi similarly ek `horizontalSign` leti hai (eye ke apne inner→outer direction se derive hui) taaki ye dono sides pe nose se door sweep kare, ek fixed "hamesha rightward" angle nahi.
  3. **`fillTaperedPath`'s fill strategy**: har point pe correct normal direction hone ke baad bhi, ek single polygon jo poora offset edge ke saath bahar jaata hai aur path ke saath wapas aata hai abhi bhi ek classic offset-curve trap hai - jahan bhi path wahan lagaye gaye offset width se tighter bend karta hai (exactly jo ek wing ka sharp launch lash line se karta hai), outer edge khud ko cross karta hai, aur ek single self-crossing filled path visually disconnected lobes ki tarah render ho sakta hai ek gap ke saath. Yehi "wing not attached"/"gap" reports actually dikha rahe the, jis bhi eye ki real corner geometry kisi diye gaye photo mein itna sharply bend hui - ek bilateral-symmetric synthetic fixture ise kabhi reproduce nahi karta, kyunki usko kabhi itna sharp bend kisi bhi side pe nahi mila. Ribbon ko chhote quads mein decompose karke fix kiya (ek per adjacent point pair), sab same rotational direction mein wound, saath mein ek `fill()` call mein filled - canvas ka nonzero winding rule phir kisi bhi quad-to-quad overlap ko solid rakhta hai, gap mein cancel karne ki jagah, aur abhi bhi ek `fill()` call hai isliye color ka apna alpha sirf ek baar blend hota hai.
     Pehle ek temporary synthetic bilateral-eye fixture se verify kiya (dono eyes, real mirrored geometry, sab 7 patterns mirror-symmetric render hote hain), phir - real-photo testing ne gap bug baar-baar surface karte rehna ke baad jo synthetic fixture reproduce nahi kar sakta tha - ek flood-fill connected-component scan se live-rendered canvas pe ek actual uploaded photo pe (North Indian model, Ruby Red, Winged/Cat-eye aur Double Wing): quad-decomposition fix se pehle, right eye ka liner 4 disconnected pixel blobs mein fragment hua (3911/1884/1042/881px) jabki left eye ek clean 5743px blob tha; fix ke baad, dono eyes exactly ek connected component render karte hain har ek (898px/861px Winged ke liye, 921px/881px Double Wing ke liye) - numerically aur wing tip ke ek pixel-level zoomed crop se dono eyes pe confirm kiya.
- **Corner-fade tail, commverse ke apne reference implementation ke against fix kiya**: directly ek real render ke against report hua "eye ke end tak nahi pahunchta" - counter-intuitively, non-winged patterns (Classic Thin, Bold/Thick, Smokey/Smudged, Tightline) already outer corner landmark pe exactly _full peak width_ pe the; problem ulta tha - stroke wahan ek hard, flat, rectangular cut mein khatam hota tha, har real liner ke apne outer (aur inner) end ke paar jo soft taper-to-a-point hota hai wo nahi. `src/commverse` ka apna eyeliner implementation directly check kiya: uska apna traced path har corner ke paar kuch _extra_ landmarks include karta hai (lower lid se borrowed), purely ek width "runway" ki tarah use hote hue - uska apna data corner ko khud full width pe rakhta hai, phir sirf un extra points ke across near-zero tak fade hota hai, corner ke paar. Same effect reproduce kiya commverse ke apne specific extra landmark indices pe depend kiye bina (jisme `LEFT/RIGHT_EYE_UPPER_INDICES` extend karna padta, jo EYESHADOW/EYEBROW/MASCARA/LASHES bhi read karte hain - is ek finish tak scoped fix ke liye bahut zyada blast radius): `renderCornerFadeTail` (utils/tryon-utils/eye.ts) ek short extension geometrically synthesize karta hai, stroke ke apne local end direction ke saath continue karte hue eye width ke ek chhote ratio se, us end ki apni real width se zero tak taper karte hue - `renderTaperedStrokeForEye` ke dono ends pe unconditionally apply hota hai, isliye KAJAL (same shared primitive) ko identical fix free mein milta hai. Ek winged pattern ke liye, outer end ki apni width already wing ki apni near-zero tip hai, isliye wahan added tail ek harmless no-op hai; har doosra pattern ek real, pehle-missing fade paata hai. Same North Indian/Ruby Red photo ke against verify kiya: dono eyes ke outer corners ab ek soft point tak taper karte hain jo eye ke apne edge ke visibly paar extend karta hai (Classic Thin, Bold/Thick directly check kiye), winged patterns unchanged (abhi bhi gap-free, abhi bhi cleanly attached).
- **`pattern` ek naya state dimension ki tarah**: `IEyeTryOnState extends IMakeupState<TEyeFinish>` ek `pattern: string | null` field add karta hai (LIP/FACE ke `IMakeupState` ka khud koi aisa field nahi hai - ye EYE-only hai, extension se add kiya gaya, shared base ko touch kiye bina). `IEyeRenderParams` (`IRenderEffectBaseParams` extend karta hai, same object-param convention jispe LIP/FACE retrofit hue the) `rgb` aur `pattern` add karta hai. `TryOnModal` ka shared narrow ref type (`ITryOnStageColorRangeRef`) ko ek optional `pattern?: string` field mila taaki same ref shape teeno categories cover kare - LIP/FACE engines ise runtime pe simply kabhi receive nahi karte.
- **Unsupported EYE finishes kuch render nahi karte, ek fallback effect nahi**: LIP (MATTE pe fallback karta hai) aur FACE (FOUNDATION pe fallback karta hai) ke ulat, `EyeEngineBase` KAJAL/EYESHADOW/EYEBROW/MASCARA/LASHES/BROWGEL ke liye rendering poori tarah skip karta hai (ek console warning ke saath). Wo alag _product types_ hain alag regions pe apply hote hue, LIP ki finishes jaisa ek effect ke variants nahi - EYESHADOW pick ke liye EYELINER ki apni rendering paint karna poora galat region paint kar dega, isliye koi sensible fallback substitute karne layak nahi hai.
- **Ise verify karte waqt ek pre-existing, unrelated bug mila aur fix hua**: `TRYON_MODEL_IMAGES` (`constants/tryon-constants/index.ts`) ek stale path pe point kar raha tha, isi wajah se pehla hi live-photo test "Couldn't process photo" ke saath fail hua (console se confirm kiya: `Failed to load image: .../models/North-Indian.webp`, ek 404) - kisi EYE code se unrelated, is session ki apni verification unblock karne ke part ki tarah fix kiya.
- **Ab tak ki verification**: `tsc -b --force`, `eslint`, aur poori `vitest` suite (74/74, 8 naye `applyEyelinerEye` smoke tests samet - sab 7 patterns + ek "unrecognized pattern id renders nothing" safety-net case) sab pass hoti hai. Synthetic checks se aage, ye is session ki **pehli FACE/EYE finish hai jo browser mein ek real uploaded photo ke against actual pixel-level confirmation se verify hui** (sirf "screenshot mein sahi dikhta hai" nahi): live-rendered canvas ka apna pixel data sample kiya aur dono eyes pe lash line pe exact expected Ruby Red-tinted color mila (`rgb(160,43,46)` vs. shade ka apna `#B0202E` alpha 0.7 pe blended), roughly symmetric extent ke saath (Winged ke liye 166/157 px, Tightline pe switch karne ke baad 55/53 px - confirm karta hai ki pattern picker genuinely render badalta hai, sirf UI selection state nahi). Wing self-intersection fix ke baad (upar Design notes dekho), real photo pe ek flood-fill connected-component scan se dono wing-bearing patterns (Winged/Cat-eye, Double Wing) ke across re-verify kiya - har baar per eye ek clean connected blob, plus dono wing tips ka ek pixel-level zoomed crop confirm karta hai ek smooth, fully-attached taper koi visible gap ya kink ke bina.
