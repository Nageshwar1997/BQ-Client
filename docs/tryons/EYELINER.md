## Design notes

- **The shared tapered-stroke primitive**: every pattern is one continuous filled path following the upper lash line (`LEFT_EYE_UPPER_INDICES`/`RIGHT_EYE_UPPER_INDICES`, `constants/tryon-constants/eye.ts`), with a per-`t` width function (`lashToWingWidth`) - thin near the inner corner, thicker near the outer, optionally continuing into a curved "wing" extension past the outer corner. Classic Thin/Bold Thick/Tightline are just different base/peak width ratios on this one primitive; Winged/Double Wing add the wing; Smokey/Smudged adds a `ctx.filter` blur pass (same technique LIP's own `LINER` finish already established); Underliner adds a second pass tracing the lower arc. All widths/lengths are ratios of the eye's own detected width (inner-to-outer corner distance), not fixed pixels - same "scale off the feature's own size" convention every other placement constant in this app follows.
- **Mirror-safe geometry - the hardest part of this finish**: MediaPipe's own eye-ring indices aren't labeled "inner"/"outer" in a side-independent way, and the left/right eye arcs run in genuinely mirrored directions. Two things had to be direction-agnostic to work correctly on both eyes:
  1. `orderInnerToOuter` - determines which end of an arc is the inner (nasal) corner by comparing each end's x-distance to the nose tip at render time, rather than trusting a fixed index to always mean "inner".
  2. `outwardNormal` - the width offset direction is computed as "away from the eye's own centroid" (`point - eyeCenter`, normalized), not derived from the local path tangent - a tangent-rotation formula only points the correct way for one specific path direction, which would come out correct for one eye and inverted for the other. The wing's own direction similarly takes a `horizontalSign` (derived from the eye's own inner→outer direction) so it sweeps away from the nose on both sides, not a fixed "always rightward" angle.
     This was verified explicitly with a temporary synthetic bilateral-eye fixture (both eyes, real mirrored geometry, a real nose-tip point) - all 7 patterns render correctly mirror-symmetric on both eyes (wing curves up-and-away-from-nose on both sides, underliner bulges down-and-away on both sides), not just "doesn't throw" the way the sunflower-spiral smoke-test fixture alone would confirm.
- **`pattern` as a new state dimension**: `IEyeTryOnState extends IMakeupState<TEyeFinish>` adds a `pattern: string | null` field (LIP/FACE's `IMakeupState` itself has no such field - this is EYE-only, added by extension rather than touching the shared base). `IEyeRenderParams` (extends `IRenderEffectBaseParams`, the same object-param convention LIP/FACE were retrofitted to) adds `rgb` and `pattern`. `TryOnModal`'s shared narrow ref type (`ITryOnStageColorRangeRef`) gained an optional `pattern?: string` field so the same ref shape covers all three categories - LIP/FACE engines simply never receive it at runtime.
- **Unsupported EYE finishes render nothing, not a fallback effect**: unlike LIP (falls back to MATTE) and FACE (falls back to FOUNDATION), `EyeEngineBase` skips rendering entirely (with a console warning) for KAJAL/EYESHADOW/EYEBROW/MASCARA/LASHES/BROWGEL. Those are different _product types_ applied to different regions, not variants of one effect the way LIP's finishes are - painting EYELINER's own rendering for an EYESHADOW pick would paint the wrong region entirely, so there's no sensible fallback to substitute.
- **A pre-existing, unrelated bug found and fixed while verifying this**: `TRYON_MODEL_IMAGES` (`constants/tryon-constants/index.ts`) pointed at a stale path, which is why the very first live-photo test failed with "Couldn't process photo" (confirmed via console: `Failed to load image: .../models/North-Indian.webp`, a 404) - unrelated to any EYE code, fixed as part of unblocking this session's own verification.
- **Verification done so far**: `tsc -b --force`, `eslint`, and the full `vitest` suite (74/74, including 8 new `applyEyelinerEye` smoke tests - all 7 patterns + one "unrecognized pattern id renders nothing" safety-net case) all pass. Beyond the synthetic checks, this is the **first FACE/EYE finish in this session verified against a real uploaded photo in the browser with actual pixel-level confirmation** (not just "looks right in a screenshot"): sampled the live-rendered canvas's own pixel data and found the exact expected Ruby Red-tinted color (`rgb(160,43,46)` vs. the shade's own `#B0202E` blended at alpha 0.7) at the lash line on both eyes, with roughly symmetric extent (166/157 px for Winged, dropping to 55/53 px after switching to Tightline - confirming the pattern picker genuinely changes the render, not just the UI selection state).
