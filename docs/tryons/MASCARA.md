> **Per-subcategory tracker** — same convention [EYELINER.md](./EYELINER.md)/[KAJAL.md](./KAJAL.md)/[EYESHADOW.md](./EYESHADOW.md)/[EYEBROW.md](./EYEBROW.md)/[BROWGEL.md](./BROWGEL.md) established: as a subcategory gets built, it gets its own dedicated tracker file and [EYE.md](./EYE.md)'s own inline checklist for it gets replaced with a summary-row + link.

> **Genuinely nayi "lash-stroke" primitive chahne wali pehli EYE finish**: isse pehle ki har EYE finish ek existing rendering shape reuse karti thi (tapered-stroke-along-an-arc primitive, ya closed-region fill) - MASCARA EYE-PLAN.md ka apna "Hard" tier hai, flag kiya gaya ki naye code ki zaroorat hai, sirf naye tuning ki nahi. [`applyMascaraEye`](../../src/utils/tryon-utils/eye.ts) upper lash line pe rooted kayi individual small curved, tapering strokes draw karta hai - phir bhi almost poori tarah existing pieces se bana hai (`fillTaperedPath` taper ke liye, same "ek direction ko absolute up ki taraf blend karo" technique jo EYEBROW ka apna `strokeAngleBiasDeg` already use karta hai, `strokeJitter` ka deterministic hash natural per-lash variation ke liye), bas ek nayi shape mein recombine kiya jo baaki kisi finish ko nahi chahiye thi. 4 patterns: Natural, Volumizing, Dramatic/Length, Curled.

## Design notes

- **Isse pehle wali har EYE finish ke ulat, isko genuinely naya code kyun chahiye tha**: EYELINER/KAJAL ek arc ke saath ek continuous stroke trace karte hain; EYESHADOW ek region wash karta hai; EYEBROW ek closed region fill karta hai ya usme hair-strokes draw karta hai. Mascara real life mein ek continuous shape jaisa bilkul nahi dikhta - ye dozens individual lash hairs hain, har ek apni root, apna curl, apni length ke saath - isliye render ko many independent short curved shapes generate aur fill karne chahiye the, ek continuous path nahi, jo pehle ki kisi bhi finish ke apne primitives directly support nahi karte the.
- **Lash curl ek rotating direction hai, ek Bezier bulge nahi**: `buildLashPoints` `steps` short straight segments walk karta hai jinki apni direction lash ke apne root angle se straight-up (`rotateTowardUp`) ki taraf gradually rotate hoti hai `curlFraction` ki doori tak, ek quadratic-curve bulge banane ki jagah jaisa EYELINER ka apna wing (`buildWingPoints`) karta hai. Ek rotating-direction walk ek real lash ke apni length ke saath curl karne ka (root se tip tak increasingly upward) ek single symmetric bulge se zyada faithful model hai, aur exact "ek direction ko absolute up ki taraf blend karo" idea reuse karta hai jo EYEBROW ka apna `strokeAngleBiasDeg` already apne Feathered/Fluffy pattern ke liye establish kar chuka tha - wahan dono eyes pe already mirror-safe proven, isliye yahan koi naya mirror-safety risk nahi.
- **Har lash abhi bhi same tapered-ribbon primitive se bana hai jo har doosri stroke-based EYE finish share karti hai**: ek baar `buildLashPoints` curved point sequence produce kar de, `fillTaperedPath(tempCtx, lashPoints, center, (t) => width * (1 - t), color)` actual fill handle karta hai - root pe thick, tip pe ek fine point tak taper - same gap-proof quad-decomposed ribbon technique jo EYELINER ka apna wing-gap fix is session mein pehle establish kar chuka tha. Ye finish banate waqt koi naya fill-robustness risk introduce nahi hua.
- **Root direction aur Dramatic/Length ka fan-out dono same mirror-safe machinery se aate hain jo already EYELINER/KAJAL ke liye proven hai**: har lash ki root direction lash line ke apne `outwardNormalsAlongPath` value se aati hai us point pe (continuity-propagated, per-point centroid-tested nahi, isi sign-flip bug class se bachte hue jise EYELINER ke apne wing ko fix karne mein do iterations lage the) - `Dramatic/Length` ka apna `fanOutDeg` phir us root direction mein ek chhota extra rotation add karta hai, dono lash line ke saath stroke kahan baithta hai aur `horizontalSign` (same mirror-safe "outer corner ki taraf konsi literal direction hai" value jo EYELINER ka wing already compute karta hai) se scaled - isliye fan dono eyes pe correctly temple ki taraf sweep karta hai, ek fixed screen-direction sirf ek side ke liye sahi hone ki jagah.
- **Deterministic per-lash variation, `Math.random()` nahi**: `strokeJitter` (EYEBROW ke apne hair-strokes ke liye already establish hui) har lash ki apni length/curl/width ko ek reproducible sine-based hash se vary karti hai uske index pe keyed - isliye same photo hamesha pixel-identical mascara render karta hai aur is file ke apne smoke tests deterministic rehte hain - real lashes kabhi perfectly uniform nahi hoti, aur ek mechanically identical repeat ek stroke shape ka obviously synthetic dikhta.
- **Range bounds shuru se hi pre-boosted the, hard way se discover nahi hue**: `EYE_RANGE_BOUNDS.MASCARA` (`{min:0.3,max:0.85,default:0.6}`) ne "ek thin individual stroke ko real texture ke against read hone ke liye ek boosted alpha range chahiye" lesson shuru se hi apply kiya, ek soft placeholder ship karke wahi lesson rediscover karne ki jagah jo EYELINER/KAJAL/EYEBROW ke apne placeholders ko real-photo testing se dhoondhna pada tha.
- **Pattern-preview icons**: 4 icons (`public/images/tryon/eye/mascara/*.webp`) har doosri EYE finish ke apne icon set ka same base template reuse karte hain, ek one-off `canvas`-package Node script se generate kiye (commit nahi kiya, har doosri EYE finish ke apne icon generation jaisa hi temporary-tooling treatment) jo `rotateTowardUp`/`buildLashPoints` directly reimplement karta hai taaki preview real renderer ke apne output ka faithful match ho, sirf ek approximation nahi.
- **Ab tak ki verification**: `tsc -b --force`, `eslint`, aur poori `vitest` suite (102/102, 6 naye `applyMascaraEye` smoke tests samet - sab 4 patterns, ek unrecognized-pattern-id case, aur ek EYELINER-id-cross-contamination case) sab pass hoti hai. Real-photo browser verification (North Indian model, Ruby Red, sab 4 patterns): har pattern dono eyes pe symmetrically render hota hai ek visibly distinct look ke saath (Natural ke fine, sparse strokes; Volumizing ka denser/thicker coverage; Dramatic/Length ke longer strokes outer corner ki taraf fan out karte hain; Curled ka tips pe zyada pronounced upward bend) - aur Natural aur Volumizing ke beech ek pixel-diff ne 1,689 genuinely changed pixels paaye, confirm karta hai ki pattern picker actually render badalta hai, sirf UI state toggle nahi karta.
