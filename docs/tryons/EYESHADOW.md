# EYESHADOW Try-On Tracker

[← Back to master tracker](./README.md) · [← Back to EYE category](./EYE.md) · [← Build plan](./EYE-PLAN.md)

_Tracking model: face landmarks (eye-ring region - upper lash-line arc, nose tip). Depends on the shared face-landmark engine — see [README.md](./README.md#shared-prerequisites-ye-pehle-banao--sabko-block-karte-hain)._

> **Per-subcategory tracker** — same convention [EYELINER.md](./EYELINER.md)/[KAJAL.md](./KAJAL.md) established: as a subcategory gets built, it gets its own dedicated tracker file and [EYE.md](./EYE.md)'s own inline checklist for it gets replaced with a summary-row + link.

> **The first EYE finish that washes a whole region, not a thin stroke**: EYELINER/KAJAL are both the same tapered-stroke-along-an-arc primitive; EYESHADOW is genuinely new rendering ([`applyEyeshadowEye`](../../src/utils/tryon-utils/eye.ts)) - a color wash across the eyelid (lash line up to a synthesized crease line), built by reusing the _existing_ tapered-ribbon geometry (`fillTaperedPath`/`buildTaperedRibbonPath`/`outwardNormalsAlongPath`) for a much taller, region-sized offset instead of a stroke width, plus two techniques ported from FACE (`mixTowardWhite`/`mixTowardBlack` per-channel color shifts, linear/radial gradients) duplicated into `eye.ts` per this file's own self-contained-per-category convention. 6 patterns: Single Wash, Two-Tone Gradient, Smokey Eye, Cut Crease, Halo Eye, Under-Eye Smudge.

## Design notes

- **The synthesized "crease" line**: no dedicated MediaPipe landmark ring exists for the eyelid crease (only the lash-line ring and the eyebrow ring are real tracked points), so the crease used everywhere below is an _offset_ of the upper lash-line arc, computed with the exact same `outwardNormalsAlongPath` direction-math EYELINER/KAJAL already use for their own width offset - just applied at a much larger, region-sized distance instead of a stroke width. Same "approximate off a real landmark rather than inventing a new tracked point" reasoning `applyForeheadExtension` (face.ts) already uses for FOUNDATION's own hairline-to-forehead extension.
- **The band's own height curve, and why it never tapers all the way to zero**: `eyelidBandHeight` shapes a smooth arch across the lid (`Math.sin(Math.PI * t) ** sharpness`, peak at the middle) - one `peakSharpness` tuning knob reshapes the whole curve (below 1 flattens it into a wider plateau, above 1 narrows it into a tighter peak), instead of needing a second "how much of the ends taper" parameter the way that would otherwise require. The curve is then lifted by `MIN_BAND_HEIGHT_RATIO` so it never actually reaches 0 at the two corners the way a plain `sin(pi*t)` would - an early version tapered literally to a knife-edge exactly at each corner landmark, which on a real photo doesn't reliably rasterize as visible color for the last stretch before the corner (the same "technically drawing something, but too thin to actually see" lesson EYELINER's own `baseWidthRatio` bump already discovered), reading as the wash stopping short with a visible gap rather than reaching the eye's own true corner - reported directly against a real render, fixed by giving the band a real minimum width all the way to both ends instead of a mathematical taper to zero.
- **Every pattern blurs its own edges by at least `BASE_EDGE_BLUR_RATIO`**: real eyeshadow never has a razor-sharp boundary against bare skin - even "Single Wash" is expected to read as blended, not as a flat, sticker-like shape (this was direct shopper feedback against a real render, matching reference images of real eyeshadow application: color reaching fully to the outer corner _and_ fading softly into skin toward the crease/brow side). `tuning.blurRatio` (Smokey Eye/Under-Eye Smudge's own stronger diffusion) only ever asks for _more_ blur on top of this baseline, never less. Two-Tone Gradient/Halo Eye's own highlight layer is built as a direct **fill** of the tapered-ribbon path (not a `ctx.clip()` + full-canvas `fillRect`, which was the first version) specifically so `ctx.filter` blur can actually soften _its_ edge too - a hard clip boundary stays a crisp boolean mask no matter what filter is active on the fill happening inside it, which would have left the highlight layer's own edge sharp even after the base wash beneath it got a soft one.
- **Reusing EYELINER's own ribbon geometry for a _region_ instead of a stroke**: `fillTaperedPath`(`ctx, lashPts, center, heightFn, color`) - unchanged from EYELINER's own function - produces exactly the eyelid-wash shape needed when `heightFn` is interpreted as "how far up from the lash line" instead of "how wide the liner is here". `buildTaperedRibbonPath` (the same path-building logic, extracted so callers can fill it with something other than a flat color) is what makes Two-Tone Gradient/Halo Eye's own gradient fills possible. The Cut Crease pattern needed the offset points directly (not just a filled shape), which is why `offsetPointsAlongNormals` was factored out of `fillTaperedPath`'s own internals rather than duplicated.
- **Two-tone/darkened tones come from the shopper's own shade, not a second arbitrary color**: `mixTowardWhite`/`mixTowardBlack` (duplicated from face.ts's own identically-named functions, per this file's self-contained-per-category convention) shift the chosen shade's own RGB toward white or black by a ratio - same "read as the real cosmetic effect, not just a colored patch" reasoning FACE's own `HIGHLIGHTER_WHITEN_RATIO`/`CONTOUR_DARKEN_RATIO` already established for HIGHLIGHTER/CONTOUR. Two-Tone Gradient's own "lighter near the brow bone" is an approximation - without real brow-bone landmarks, the band's own synthesized top edge (the crease line) stands in for "up near the brow area" too.
- **Dispatch by tuning-field presence, not a pattern-id switch**: `applyEyeshadowForEye` checks which optional `IEyeshadowPatternTuning` fields are set (`concentratedHeightRatio` → Smokey/Under-Eye Smudge's second pass, `creaseLineWidthRatio` → Cut Crease's crease stroke, `highlightRatio` alone vs. `highlightRatio` + `darkenRatio` together → Two-Tone's linear gradient vs. Halo's radial glow, `underSmudgeHeightRatio` → the lower-arc pass) - same convention `renderTaperedStrokeForEye` (EYELINER/KAJAL) already established, rather than switching on the pattern id string directly.
- **Pattern-preview icons, matching the family's visual language with one deliberate difference**: the 6 icons (`public/images/tryon/eye/eyeshadow/*.webp`) reuse the same base template (light-gray lid-crease arc, gray iris + white highlight) EYELINER/KAJAL's own icons use, generated with a one-off `canvas`-package Node script (not checked in, same temporary-tooling treatment as KAJAL's own icon generation), converted PNG→WebP via `cwebp`. Unlike EYELINER/KAJAL's black-ink previews (which intentionally show _shape only_, since color there always comes from the separate shade picker and a black stroke reads naturally as liner ink), these use a representative neutral warm-taupe wash - a flat black region wouldn't read as "eyeshadow" the way it reads as "eyeliner", so color here communicates the _technique_ (wash/gradient/smudge) the same way a real eyeshadow palette swatch does.
- **A pre-existing, unrelated bug found while extending `UNSUPPORTED_EYE_FINISHES`**: none this time - `EyeEngineBase`'s finish-aware pattern-default fix (`EYE_DEFAULT_PATTERNS`) and `TryOnModal`'s matching fix were both already made correctly generic when KAJAL was built, so EYESHADOW only needed one new entry in each map - no repeat of that class of bug.
- **Verification done so far**: `tsc -b --force`, `eslint`, and the full `vitest` suite (88/88, including 8 new `applyEyeshadowEye` smoke tests - all 6 patterns, one unrecognized-pattern-id case, and one EYELINER-id-cross-contamination case) all pass. Real-photo browser verification (North Indian model, Ruby Red, all 6 patterns): every pattern renders symmetrically on both eyes with a visibly distinct look (Single Wash's clean flat coverage, Two-Tone's visible top-light/bottom-dark banding, Smokey's soft feathered edge with a deeper concentration at the lash line, Cut Crease's crisper top edge, Halo's lighter center, Under-Eye Smudge's extra smudge below the lower lash line) - and a pixel-diff between Single Wash and Under-Eye Smudge over the same region found 9,846 changed pixels, 73% of them specifically in the lower/under-eye portion of the crop, confirming the extra pass genuinely paints new pixels there rather than just toggling picker UI state.
- **The corner-coverage/blend fix, re-verified against the same real photo**: after the `MIN_BAND_HEIGHT_RATIO` floor and universal `BASE_EDGE_BLUR_RATIO` blur landed, all 6 patterns were re-checked on the same North Indian/Ruby Red photo via zoomed canvas crops - the wash now visibly reaches both eye corners with a soft feathered taper (no bare-skin gap before the corner, the exact defect a real render had shown), and the upper edge now blends gradually into skin rather than cutting off crisply, matching reference real-eyeshadow photos the shopper feedback pointed at directly. Checked specifically on Cut Crease (crisp crease line unaffected, still crisp - only the base wash beneath it softened) and Halo Eye/Two-Tone Gradient (their own highlight layer's edge now blurs consistently with the base, confirming the clip→fill rework actually took effect).
