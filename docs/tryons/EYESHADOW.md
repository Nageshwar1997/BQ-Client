# EYESHADOW Try-On Tracker

[← Back to master tracker](./README.md) · [← Back to EYE category](./EYE.md) · [← Build plan](./EYE-PLAN.md)

_Tracking model: face landmarks (eye-ring region - upper lash-line arc, nose tip). Depends on the shared face-landmark engine — see [README.md](./README.md#shared-prerequisites-ye-pehle-banao--sabko-block-karte-hain)._

> **Per-subcategory tracker** — same convention [EYELINER.md](./EYELINER.md)/[KAJAL.md](./KAJAL.md) established: as a subcategory gets built, it gets its own dedicated tracker file and [EYE.md](./EYE.md)'s own inline checklist for it gets replaced with a summary-row + link.

> **Ek poora region wash karne wali pehli EYE finish, ek thin stroke nahi**: EYELINER/KAJAL dono same tapered-stroke-along-an-arc primitive hain; EYESHADOW genuinely nayi rendering hai ([`applyEyeshadowEye`](../../src/utils/tryon-utils/eye.ts)) - eyelid ke across ek color wash (lash line se ek synthesized crease line tak), existing tapered-ribbon geometry (`fillTaperedPath`/`buildTaperedRibbonPath`/`outwardNormalsAlongPath`) ko ek stroke width ki jagah ek much taller, region-sized offset ke liye reuse karke bana, plus FACE se do techniques ported (`mixTowardWhite`/`mixTowardBlack` per-channel color shifts, linear/radial gradients) is file ke apne self-contained-per-category convention ke hisaab se `eye.ts` mein duplicate ki gayi. 6 patterns: Single Wash, Two-Tone Gradient, Smokey Eye, Cut Crease, Halo Eye, Under-Eye Smudge.

## Design notes

- **Synthesized "crease" line**: eyelid crease ke liye koi dedicated MediaPipe landmark ring exist nahi karti (sirf lash-line ring aur eyebrow ring hi real tracked points hain), isliye crease jo har jagah neeche use hoti hai wo upper lash-line arc ka ek _offset_ hai, exact same `outwardNormalsAlongPath` direction-math se compute kiya jo EYELINER/KAJAL already apne width offset ke liye use karte hain - bas ek much larger, region-sized distance pe apply kiya, stroke width ki jagah. Same "ek real landmark se approximate karo, ek naya tracked point invent mat karo" reasoning jo `applyForeheadExtension` (face.ts) already FOUNDATION ke apne hairline-to-forehead extension ke liye use karta hai.
- **Band ka apna height curve, aur ye kabhi zero tak taper kyun nahi karta**: `eyelidBandHeight` lid ke across ek smooth arch shape banata hai (`Math.sin(Math.PI * t) ** sharpness`, beech mein peak) - ek `peakSharpness` tuning knob poori curve reshape karta hai (1 se neeche ek wider plateau mein flatten karta hai, 1 se upar ek tighter peak mein narrow karta hai), ek doosre "ends kitna taper karte hain" parameter ki zaroorat ki jagah jo warna chahiye hota. Curve ko phir `MIN_BAND_HEIGHT_RATIO` se lift kiya jaata hai taaki ye dono corners pe actually kabhi 0 tak na pahunche, jaisa ek plain `sin(pi*t)` karta. Ek early version literally ek knife-edge tak taper karta tha exactly har corner landmark pe, jo ek real photo pe reliably visible color ki tarah rasterize nahi hota corner se pehle ke last stretch ke liye (same "technically kuch draw kar raha hai, lekin dekhne layak itna thin hai" lesson jo EYELINER ka apna `baseWidthRatio` bump already discover kar chuka tha), wash corner se short rukta hua ek visible gap ke saath dikhta tha, eye ke apne true corner tak pahunchne ki jagah - directly ek real render ke against report hua, band ko dono ends tak ek real minimum width dekar fix kiya, zero tak ek mathematical taper ki jagah.
- **Har pattern apne edges ko kam se kam `BASE_EDGE_BLUR_RATIO` se blur karta hai**: real eyeshadow ka bare skin ke against kabhi razor-sharp boundary nahi hota - "Single Wash" bhi blended dikhna expected hai, ek flat, sticker-like shape nahi (ye direct shopper feedback tha ek real render ke against, real eyeshadow application ki reference images se match karte hue: color outer corner tak fully pahunchna _aur_ crease/brow side ki taraf skin mein softly fade hona). `tuning.blurRatio` (Smokey Eye/Under-Eye Smudge ka apna stronger diffusion) is baseline ke upar sirf _zyada_ blur maangta hai, kam kabhi nahi. Two-Tone Gradient/Halo Eye ka apna highlight layer directly tapered-ribbon path ka ek **fill** ki tarah bana hai (ek `ctx.clip()` + full-canvas `fillRect` nahi, jo pehla version tha) specifically taaki `ctx.filter` blur actually _uska_ edge bhi soften kar sake - ek hard clip boundary ek crisp boolean mask reh jaata hai chahe fill ke andar chalne wala filter kuch bhi ho, jisse highlight layer ka apna edge sharp reh jaata neeche wale base wash ko ek soft edge milne ke baad bhi.
- **EYELINER ke apne ribbon geometry ko ek _region_ ke liye reuse karna, ek stroke ki jagah**: `fillTaperedPath`(`ctx, lashPts, center, heightFn, color`) - EYELINER ke apne function se unchanged - exactly wo eyelid-wash shape produce karta hai jab `heightFn` ko "lash line se kitna upar" ki tarah interpret kiya jaaye, "liner yahan kitna wide hai" ki jagah. `buildTaperedRibbonPath` (same path-building logic, extract ki gayi taaki callers ise flat color ke alawa kisi aur cheez se fill kar sakein) hai jo Two-Tone Gradient/Halo Eye ke apne gradient fills ko possible banata hai. Cut Crease pattern ko offset points directly chahiye the (sirf ek filled shape nahi), isi liye `offsetPointsAlongNormals` ko `fillTaperedPath` ke apne internals se factor out kiya gaya, duplicate karne ki jagah.
- **Two-tone/darkened tones shopper ke apne shade se aate hain, ek doosre arbitrary color se nahi**: `mixTowardWhite`/`mixTowardBlack` (face.ts ke apne identically-named functions se duplicate kiye, is file ke self-contained-per-category convention ke hisaab se) chosen shade ke apne RGB ko ek ratio se white ya black ki taraf shift karte hain - same "real cosmetic effect ki tarah read ho, sirf ek colored patch nahi" reasoning jo FACE ka apna `HIGHLIGHTER_WHITEN_RATIO`/`CONTOUR_DARKEN_RATIO` already HIGHLIGHTER/CONTOUR ke liye establish kar chuka tha. Two-Tone Gradient ka apna "brow bone ke kareeb lighter" ek approximation hai - real brow-bone landmarks ke bina, band ka apna synthesized top edge (crease line) hi "brow area ke upar kareeb" ke liye bhi stand in karta hai.
- **Dispatch tuning-field presence se, ek pattern-id switch se nahi**: `applyEyeshadowForEye` check karta hai ki kaunse optional `IEyeshadowPatternTuning` fields set hain (`concentratedHeightRatio` → Smokey/Under-Eye Smudge ka second pass, `creaseLineWidthRatio` → Cut Crease ka crease stroke, `highlightRatio` akela vs. `highlightRatio` + `darkenRatio` saath mein → Two-Tone ka linear gradient vs. Halo ka radial glow, `underSmudgeHeightRatio` → lower-arc pass) - same convention jo `renderTaperedStrokeForEye` (EYELINER/KAJAL) already establish kar chuka tha, pattern id string pe directly switch karne ki jagah.
- **Pattern-preview icons, family ki visual language match karte hue ek deliberate difference ke saath**: 6 icons (`public/images/tryon/eye/eyeshadow/*.webp`) same base template reuse karte hain (light-gray lid-crease arc, gray iris + white highlight) jo EYELINER/KAJAL ke apne icons use karte hain, ek one-off `canvas`-package Node script se generate kiye (commit nahi kiya, KAJAL ke apne icon generation jaisa hi temporary-tooling treatment), PNG→WebP `cwebp` se convert kiya. EYELINER/KAJAL ke black-ink previews ke ulat (jo intentionally sirf _shape_ dikhate hain, kyunki wahan color hamesha alag shade picker se aata hai aur ek black stroke naturally liner ink ki tarah read hota hai), ye ek representative neutral warm-taupe wash use karte hain - ek flat black region "eyeliner" jaisa read hota hai, "eyeshadow" jaisa nahi, isliye yahan color _technique_ (wash/gradient/smudge) communicate karta hai, waise hi jaise ek real eyeshadow palette swatch karta hai.
- **`UNSUPPORTED_EYE_FINISHES` extend karte waqt ek pre-existing, unrelated bug**: is baar koi nahi - `EyeEngineBase` ka finish-aware pattern-default fix (`EYE_DEFAULT_PATTERNS`) aur `TryOnModal` ka matching fix dono already correctly generic bana diye gaye the jab KAJAL bana, isliye EYESHADOW ko sirf ek naya entry chahiye tha har map mein - us bug class ka koi repeat nahi.
- **Ab tak ki verification**: `tsc -b --force`, `eslint`, aur poori `vitest` suite (88/88, 8 naye `applyEyeshadowEye` smoke tests samet - sab 6 patterns, ek unrecognized-pattern-id case, aur ek EYELINER-id-cross-contamination case) sab pass hoti hai. Real-photo browser verification (North Indian model, Ruby Red, sab 6 patterns): har pattern dono eyes pe symmetrically render hota hai ek visibly distinct look ke saath (Single Wash ka clean flat coverage, Two-Tone ka visible top-light/bottom-dark banding, Smokey ka soft feathered edge lash line pe ek deeper concentration ke saath, Cut Crease ka crisper top edge, Halo ka lighter center, Under-Eye Smudge ka extra smudge lower lash line ke neeche) - aur same region pe Single Wash aur Under-Eye Smudge ke beech ek pixel-diff ne 9,846 changed pixels paaye, jinme se 73% specifically crop ke lower/under-eye portion mein the, confirm karta hai ki extra pass genuinely naye pixels wahan paint karta hai, sirf picker UI state toggle nahi karta.
- **Corner-coverage/blend fix, same real photo ke against re-verified**: `MIN_BAND_HEIGHT_RATIO` floor aur universal `BASE_EDGE_BLUR_RATIO` blur land hone ke baad, sab 6 patterns same North Indian/Ruby Red photo pe zoomed canvas crops se re-check kiye gaye - wash ab visibly dono eye corners tak ek soft feathered taper ke saath pahunchta hai (corner se pehle koi bare-skin gap nahi, exactly wo defect jo ek real render ne dikhaya tha), aur upper edge ab gradually skin mein blend hota hai, crisply cut off hone ki jagah, reference real-eyeshadow photos se match karte hue jinki taraf shopper feedback ne directly point kiya tha. Specifically Cut Crease pe check kiya (crisp crease line unaffected, abhi bhi crisp - sirf neeche wala base wash soften hua) aur Halo Eye/Two-Tone Gradient pe (unka apna highlight layer ka edge ab base ke saath consistently blur hota hai, confirm karta hai ki clip→fill rework actually effect mein aaya).
